# Архитектура Оркестрации Мультиагентной Системы (Multi-Agent Orchestration Architecture)

**Проект:** MCP Rooms Marketplace (`LeonidYasin/mcp-rooms-googleai-2`)
**Роль:** Архитектор и CTO проекта
**Идеология:** MCP-First, равноправие людей и ИИ-агентов, прозрачность состояния в SQLite, честность вызовов без подлога.

---

## 🏛️ 1. Философия и Базовые Принципы Оркестрации

Система оркестрации проектируется не как монолитный централизованный контроллер, а как **децентрализованный, гармоничный протокол взаимодействия автономных специализированных агентов** вокруг единой шины данных и состояний (SQLite DB + MCP JSON-RPC + SSE).

### Ключевые принципы:
1. **Единый источник правды (Single Source of Truth):**
   Все состояния комнат, объявлений, профилей, аудита и прав фиксируются исключительно в постоянной базе данных SQLite (`mcp_rooms.db`). Агенты не хранят скрытого непубличного состояния.
2. **Равноправие Агентов и Людей (Human-Agent Parity):**
   Агенты взаимодействуют по тем же протоколам и правилам, что и люди — через стандартизированный MCP JSON-RPC (`POST /mcp`) и REST API с Bearer-ключами авторизации.
3. **Изоляция и Принцип наименьших привилегий (Least Privilege RBAC):**
   Каждый агент имеет свой идентификатор принципала (`agent:<slug>`) и индивидуальный набор разрешённых областей (`scopes`: `listings:read/write`, `rooms:read/write`, `chat:write`). Агент не может читать или писать в чужие комнаты.
4. **Прозрачность и Неотвратимость Аудита (Auditability):**
   Каждое действие агента (создание объявления, публикация, отправка сообщения, загрузка файла) автоматически трассируется в системную таблицу `audit_logs`.
5. **Честность Рантайма (Honesty Rule):**
   Запрещено подделывать статусы согласий (`safetyConfirmed`), фальсифицировать вызовы инструментов (`executedTools`) или маскировать шаблоны под живые ответы ИИ-модели. Если модель недоступна, возвращается честный `degraded` статус.

## 🎭 2. Ролевая Специализация Агентов в Проекте

Каждая сессия ИИ-агента или автономный сервисный агент выступает в одной из чётко определённых ролей:

| Роль Агента | Назначение / Зона ответственности | Затронутые модули | Необходимые RBAC Scopes |
| :--- | :--- | :--- | :--- |
| **Architect Agent (CTO)** | Аудит состояния репо, проектирование ТЗ, роадмэп, оркестрация пула задач, контроль CI/CD. | `docs/`, `AGENTS.md` | `admin`, `*` |
| **Protocol & Core Agent** | Бэкенд, REST/MCP эндпоинты, авторизация, SQLite схема, транзакции, SSE поток. | `server/`, `server.ts` | `listings:write`, `rooms:write` |
| **Frontend & UI Agent** | Клиентский интерфейс (React + Tailwind), консоль MCP, модальные окна, интеграция API. | `src/`, `index.html` | `listings:read`, `rooms:read` |
| **QA & Abuse Agent** | Автоматизированные E2E тесты, проверки под нагрузкой, абуз-тесты (Rate Limit, XSS, SQLi). | `tests/` | `*` |
| **Ops & Security Agent** | Сборка Docker, конфигурация Caddy/Reverse Proxy, скрипты бэкапа/восстановления, CSP. | `Dockerfile`, `scripts/`, `docs/deployment.md` | `admin` |

## 🔄 3. Жизненный Цикл Задачи и Протокол Взятия (Task Lifecycle & Claiming)

Чтобы предотвратить гонки (race conditions) и затирание работы при параллельной работе нескольких агентов/сессий, вводится формальный протокол управления задачами.

### Статусы задачи:
- `⏳ Бэклог` (Backlog): Задача сформулирована, имеет ТЗ и критерии приёмки, свободна для выполнения.
- `🔄 В разработке` (In Progress): Задача захвачена агентом, зафиксирована ветка, затронутые файлы и время.
- `🔍 На ревью` (In Review): Создан PR, прогоняются тесты CI.
- `✅ Завершено` (Completed): PR успешно смержен в `main`, документ обновлён.

```
 [⏳ Бэклог] ─── (Агент проверяет пересечения файлов) ───► [🔄 В разработке]
                                                                  │
                                                        (Запуск tests & build)
                                                                  │
 [✅ Завершено] ◄─── (Слияние PR в main) ◄─── [🔍 На ревью] ◄─────┘
```

### Протокол Захвата Задачи (Task Claiming Protocol & GitHub Issues):
1. **Использование GitHub Issues как единого реестра задач:**
   Каждая задача из пула имеет соответствующий **GitHub Issue**. Агенты могут просматривать список задач через CLI:
   `python3 scripts/github_mcp_cli.py --repo LeonidYasin/mcp-rooms-googleai-2 issues list --state open`
2. **Проверка пересечений по файлам (Impact Area Analysis):**
   Перед взятием задачи агент изучает таблицу в `docs/session_coordination.md` и открытый Issue. Если затронутые файлы уже правит другой агент в статусе `🔄 В разработке`, задача не может быть взята.
3. **Атомарная фиксация захвата (Claim Record):**
   Агент обновляет `docs/session_coordination.md` (указывает сессию, ветку `feat/<task-id>` и время) и оставляет комментарий/коммит в соответствующем GitHub Issue.
4. **Автоматическое закрытие Issue при мерже:**
   В описании PR указывается `Closes #<Issue_Number>`. После успешного мержа PR в `main` Issue закрывается автоматически или через CLI (`issues close --number <N>`).
5. **Таймаут неактивности (Stale Task Timeout = 2 часа):**
   Если задача находится в статусе `🔄 В разработке` более 2 часов без обновлений, она считается заброшенной и может быть перехвачена другим агентом.

## 🤝 4. Протокол Межагентного Взаимодействия (Inter-Agent Protocol)

Агенты в системе взаимодействуют через **Shared Rooms (Комнаты Переговоров)** в рантайме и через **GitHub PR / Session Coordination** во время разработки:

1. **Разработка и Код:**
   Передача контекста между сессиями разработчиков происходит через `Handover & Blockers Log` в `docs/session_coordination.md`.
2. **Рантайм и Торговля (MCP Rooms):**
   Агенты людей и сторонних сервисов создают комнаты переговоров через MCP инструмент `join_room` и обмениваются предложениями через `send_message`. Ответы генерируются реактивным движком `server/negotiator.ts`.
