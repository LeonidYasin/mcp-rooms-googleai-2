# PR-3 — субъект, комнаты, публичная витрина

Дата: 2026-10-28. Основание: `docs/audit/2026-10-27-audit.md` (F-01) и `docs/audit/pr-plan.md` §5.
Ветка: `feat/api-keys`, база — `fix/no-fabricated-tools` (PR #3), затем `main`.

## Что изменилось

### Субъект

- Таблица `api_keys` (`server/db.ts`): `id`, `principal_id`, `name`, `digest` (sha256, UNIQUE),
  `created_at`, `last_used_at`, `revoked_at`. Плейнтекст-токен не хранится и не логируется.
- `server/auth.ts`: выпуск (`issueApiKey`), разбор `Authorization: Bearer`, `requireAuth`,
  `optionalAuth`, `isRoomParticipant`. Формат ключа — `mcr_` + 32 случайных байта (base64url).
- CLI `scripts/issue-key.ts` (`npm run key:issue`): `--principal`, `--name`, `--list`, `--revoke`.
  Principal: `user:<slug>`, `agent:<slug>`, `org:<slug>`.

### Границы доступа

| Ресурс | Правило |
| --- | --- |
| `GET /api/listings`, `GET /api/listings/:id` | анонимно, проекция `toPublicListing` (без `owner`, `profile_id`, `embedding_json`, `contact_protocols`) |
| `POST /api/listings` | ключ; `owner` = субъект, значение `owner` из тела игнорируется |
| `GET /api/rooms` | ключ; только комнаты, где субъект в `participants` |
| `GET /api/rooms/:id`, `/stream`, `POST /messages` | ключ + участник; иначе `403` |
| `POST /api/chat`, `/api/agent/negotiate*`, `GET /api/negotiations` | ключ; переговоры и созданные записи — от имени субъекта |
| `POST /mcp` `tools/list`, `resources/read listings://all` | анонимно |
| `POST /mcp` `tools/call`, `resources/read rooms://all` | ключ; `rooms://all` фильтруется по участнику |

- `join_room` больше не принимает `buyer_id`: покупатель — субъект, участники комнаты —
  `[субъект, listing.owner]`; фабрикованные `agent:counterpart`/`agent:angel` убраны.
- `send_message` не принимает `sender`: отправитель — субъект, `role` ограничена `agent|human`.
- `get_room_history` и `rooms://all` проверяют участие.
- `create_listing` (REST, MCP, чат) пишет `owner` = субъект.
- Переговорщик (`server/negotiator.ts`) принимает `principalId`; комнаты и авто-созданная
  карточка принадлежат субъекту вместо хардкода `user:client`.

### UI

- `src/lib/api.ts` — хранение ключа в localStorage, `Authorization` для fetch,
  `access_token` только для SSE.
- Кнопка 🔑 в шапке и диалог `ApiKeyModal` (вставка/очистка ключа, объяснение выдачи).
- `App`: комнаты грузятся только с ключом; при 401 они очищаются, а не остаются чужими;
  публикация и сообщения больше не «успешны локально» при ошибке сервера — показывается
  ошибка; отклик на объявление создаёт комнату через настоящий `join_room`.
- `McpChat`: ключ обязателен, 401 открывает диалог ключа, SSE подключается с токеном.
- `McpConsole`: честное сообщение, что `tools/call` без ключа вернёт 401; пустой список
  комнат объяснён.

## Тесты

- `tests/auth.test.ts`: 401 без ключа/с неверным/отозванным ключом; `tools/list` открыт,
  `tools/call` — нет; атрибуция `owner` и `sender`; изоляция комнат (список, чтение, запись,
  SSE, `rooms://all`, `get_room_history`); публичная проекция без `owner`/`embedding_json`.
- `tests/mcp-tools.test.ts`: инструменты комнат без субъекта → `authentication_required`,
  чужой субъект → `forbidden`, подмена `buyer_id` не работает.
- `tests/rest-api.test.ts`, `tests/chat-honesty.test.ts`: обновлены под обязательный ключ.

## Известные ограничения (осознанно вне PR-3)

1. Нет ролей/scope: любой действующий ключ может всё, что разрешено роли «участник».
2. Нет rate limiting и аудит-лога чтения комнат (план — PR-8/PR-11).
3. `access_token` в query для SSE может попасть в логи; заменяется в PR-8.
4. Ключ в localStorage доступен скриптам страницы; для операторских ключей это неприемлемо —
   нужен отдельный admin-контур (вне этого прототипа).
5. Существующие карточки и комнаты из сидов не привязаны к выданным ключам: они остаются
   доступны только тем субъектам, чьи id перечислены в `participants` (демо-данные убирает PR-7).
6. Публикация по-прежнему без черновика (PR-5), переговоры без модели — демо (PR-6).
