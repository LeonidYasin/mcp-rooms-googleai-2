# Сравнение: прототип `mcp-rooms-googleai-2` и `LeonidYasin/mcp-rooms`

Сравнение по состоянию на 2026-10-27: прототип — `a5fb1c1`, основной проект — `main` @ `90ad38d` (PR #32, Phase 3 legacy-refusal). Оба репозитория открыты, MIT.

## 1. Одной таблицей

| Критерий | `mcp-rooms` (основной) | `mcp-rooms-googleai-2` (прототип) |
| --- | --- | --- |
| Роль | движок продукта, owner-first пилот | демо-витрина, UX-лаборатория |
| Стек | Python 3.10–3.13, ASGI, официальный MCP SDK, Streamable HTTP | Node 22, Express 5, вручную написанный JSON-RPC, React 19 + Vite |
| MCP-совместимость | официальный SDK, сессии, версии протокола | POST `/mcp` без `initialize`/сессий → реальные клиенты не подключаются |
| Идентичность | UUID-пользователи, digest-only Bearer-ключи, scopes, TTL, отзыв | отсутствует |
| Модель доступа | участники комнаты, приватные отклики A↔B, allowlist-проекция | любой читает все комнаты и пишет от любого имени |

## 2. В чём прототип действительно сильнее

1. **Вертикальный срез в одном процессе.** Каталог, карточка, публикация, чат с агентом, комнаты — в одном приложении и одной SQLite. У основного проекта то же самое разложено на слои с гейтами, и чтобы «просто посмотреть», нужно собрать wheelhouse, ключи и unit.
2. **Асимметричный матчинг.** `matchListingAsymmetric` (`server/embeddings.ts:240-300`) сопоставляет request↔offer, а не строка-в-строку: косинус по эмбеддингам, при отсутствии ключа — лексический fallback с категорийной близостью. В основном проекте эмбеддинги сознательно отложены, и это единственная продуктовая идея прототипа, которой там нет вообще.
3. **SSE-присутствие.** Поток комнаты с `retry`, heartbeat и снапшотом даёт UX «агенты переписываются сейчас». В основном проекте real-time нет.
4. **UI-паттерны.** Категории с иконками, карточка с условиями передачи, визард публикации с предпросмотром, консоль агента, баннер принципов. Это готовый материал для read-only витрины, даже если код не переносится.
5. **Низкий порог входа.** Docker + один файл БД + `.env` — понятно внешнему разработчику. У основного проекта порог выше (сборка пакета, bootstrap, unit).
6. **Gemini tool-calling уже соединён с доменными функциями.** Петля «модель → function call → выполнение → второй проход с результатом» (`server.ts:497-560`) — рабочий образец клиента, которого нет в основном проекте.

## 3. В чём прототип слабее — и почему это не «недоработки»

- **Нет модели доступа.** Не «забыли авторизацию», а её нет в архитектуре: `sender` из тела, все комнаты в одном списке, MCP-ресурс отдаёт весь дамп. Это переписывание слоя, а не патч.
- **Нет честности данных.** Договорённости, цены и согласия синтезируются. Для площадки, где по этим экранам принимают решения, это дисквалифицирующий дефект.
- **Нет контракта публикации.** Заявленные «осознанная публикация», черновик, валидация `listing_contract` в коде отсутствуют: одна INSERT-строка.
- **Нет доказательств.** Тесты не запускаются, CI красный, деплой не проверялся.
- **Документация врёт.** Не устарела — именно описывает другой продукт (`docs/work-state.json` → `repository: LeonidYasin/mcp-rooms`).

## 4. Что это значит для решения

Прототип и основной проект решают разные задачи:

- основной проект отвечает на вопрос «можно ли безопасно провести одну реальную сделку»;
- прототип отвечает на вопрос «как это должно выглядеть и ощущаться».

Поэтому:

- **заменять** основной проект прототипом нельзя: у него нет ни одного из свойств, которые основной проект доказывал (доступ, согласие, восстановление, отзыв ключей);
- **переносить** прототип целиком тоже нельзя: его ценность — в 4–6 идеях, а не в 3,9 тыс. строк;
- **правильная стратегия** — держать прототип как UX/спец-донор, а продуктовые идеи вносить в основной проект отдельными opt-in изменениями (см. `integration-into-mcp-rooms.md`), не ломая его текущий north star «одна реальная вещь → публикация → приватный отклик».

## 5. Итоговая оценка

| | `mcp-rooms` | прототип |
| --- | --- | --- |
| Готовность к production | RC, ждёт owner-gated deploy | демо, ~30% |
| Ценность сейчас | продукт и доказательства | демонстрация и идеи |
| Что делать | продолжать по своему плану | заморозить как лабораторию или довести по `pr-plan.md` |

Если владелец выбирает «довести прототип до production» — это отдельный продукт со своим жизненным циклом, и его нельзя считать продолжением `mcp-rooms`. Если выбирает «взять идеи» — дешевле и безопаснее, и основной проект от этого только выигрывает.
