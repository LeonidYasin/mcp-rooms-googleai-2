# Интеграция идей прототипа в `LeonidYasin/mcp-rooms`

Документ отвечает на вопрос: что из `mcp-rooms-googleai-2` стоит перенести в основной проект, в какой форме и в каком порядке, не нарушая его текущие ограничения.

Базовые правила основного проекта (из `AGENTS.md`): изменения — только через отдельные owner-approved PR в `feat/standalone-identity`; новые возможности — explicit opt-in compositions, не миграции по умолчанию; никаких shell/SQL/root в MCP; CI evidence на SHA; CI ≠ TEST ≠ production. Всё ниже — предложения к обсуждению, а не разрешение на работу.

## 1. Что переносить стоит, а что нет

| Идея прототипа | Решение | Куда |
| --- | --- | --- |
| Асимметричный матчинг offer↔request на эмбеддингах + лексический fallback | **Переносить, но после явного решения владельца** — сейчас в плане проекта эмбеддинги отложены | новый opt-in tool `listings_match` |
| SSE-поток «живого присутствия» | **Частично**: публичная витрина — да; приватный тред — через MCP-нотификации, не новый HTTP-канал | `public_web.py`, `server.py` |
| Обмен условиями и фиксация согласия | **Переносить идею, не код**: typed `propose/accept` с двумя субъектами и digest | `store.py`/`response_store.py` |
| React-витрина: карточки, секции, визард публикации | **Только read-only визуальные паттерны** | `public_web.py` |
| Петля Gemini tool-calling | **Как пример клиента**, не серверный код | `clients/` |
| Демо-данные и «1 команда до демо» | **Как dev-профиль с флагом**, не production | `docs/`, compose |
| Кэш эмбеддингов в SQLite | **Переносить** вместе с матчингом | новая таблица |
| Keyword-роутинг интентов | **Не переносить** — это не агент, а `if/else` | — |
| Синтетические `executedTools` | **Не переносить** — прямое нарушение «не выдумывать» | — |
| Хардкод цен/фактов/`safetyConfirmed` | **Не переносить** | — |
| Авто-публикация из промпта | **Не переносить** — нарушает consent-модель | — |
| 20 «инструментов», которых нет | **Не переносить** | — |
| Неавторизованные дампы комнат | **Не переносить** | — |
| Унаследованные `docs/` | **Не переносить** (они и так отсюда) | — |

## 2. I1 — `listings_match`: асимметричный матчинг

**Что берём:** идею «запрос ищет предложения» вместо поиска по подстроке; косинус + лексический fallback при недоступном провайдере; честный `match_method` в ответе.

**Форма в основном проекте:**

- новый модуль `src/mcp_rooms/embeddings.py`: протокол `EmbeddingProvider.embed(texts) -> list[list[float]]`, реализации `GoogleProvider` (env `GEMINI_API_KEY`, модель из `EMBEDDING_MODEL`) и `DisabledProvider`; провайдер выбирается флагом `EMBEDDING_PROVIDER=disabled|google`;
- таблица `listing_embeddings(listing_id, publication_revision, model, dim, vector BLOB, content_digest, updated_at)` — ключ по **публикационной** ревизии, чтобы кэш инвалидировался при новой публикации;
- tool `listings_match(query, section=None, limit=10)` с `readOnlyHint=True`, в opt-in наборе (флаг конфигурации), рядом с `listings_public_index`;
- кандидаты — только `status='published'` и только allowlist-поля публичной проекции; приватные черновики и чужие данные в матчинг не попадают;
- ответ: `{ items: [{listing_id, title, section, locality, score, match_method}], provider, degraded }`; `score` — число, **без** «совпадение 87%» в тексте, если посчитан лексически: `match_method` это и показывает;
- при `disabled`/ошибке провайдера — лексический fallback, `provider: 'fallback'`, `degraded: true`.

**Гейты:**

- тесты: детерминированный fake-провайдер; кандидаты только публичные; чужой черновик не виден; fallback при `disabled`; кэш инвалидируется по ревизии; пустой запрос → `422`;
- бюджет: матчинг не должен пересчитывать эмбеддинги всего каталога на запрос — только для отсутствующих в кэше карточек, с лимитом на вызов;
- приватность: текст запроса не логируется; в ответе нет автора и контактов.

**Важное ограничение:** `docs/deployment-readiness.md` фиксирует «не добавляем… embeddings до первого результата». Поэтому I1 требует либо (а) decision record, меняющий этот порядок, либо (б) реализации **после** приёмки первого реального сценария. Второе — рекомендация: матчинг бесполезен, пока нет публикаций, на которых его проверять.

## 3. I2 — real-time

**Публичная витрина (низкий риск).** В `public_web.py` уже есть рендер индекса и карточек. Добавить `text/event-stream` для `/market` (анонимно, только публичная проекция): события `published`, `withdrawn`, `updated` с `id = publication revision`, реплей по `Last-Event-ID` из таблицы публикаций (не из памяти), лимит подписчиков, heartbeat. Ничего приватного в поток не попадает — это тот же allowlist.

**Приватный тред (высокий риск — иначе).** Не делать отдельный HTTP-SSE для `listings_thread`: это второй канал авторизации рядом с MCP, а в основном проекте авторизация — свойство транспорта и ключа. Правильно: использовать Streamable HTTP официального SDK — серверные уведомления (обновление ресурса/логирование) участнику отклика, а `listings_thread` остаётся источником истины с курсором. Тогда «живость» не создаёт нового способа утечки.

**Что не переносить:** снапшот «все сообщения комнаты» при подключении (в прототипе — `server.ts:305`) и подписку без проверки участника.

## 4. I3 — согласование условий без выдуманного согласия

**Что берём:** идею, что стороны могут зафиксировать условия в комнате. **Что не берём:** захардкоженные диалоги, цены и `safetyConfirmed: true`.

**Форма:** в основном проекте уже есть правильный паттерн — `listings_confirm_publication(preview_digest, consent, client_id)` и receipts в `publication_store.py`. Его и переиспользовать:

- `rooms_terms_propose(room_id, terms: TypedTerms, client_id)` — создаёт предложение с digest и версией;
- `rooms_terms_accept(room_id, proposal_id, terms_digest, client_id)` — принимает **другой** субъект; повторный accept идемпотентен, accept своего предложения запрещён;
- `rooms_agreement_get(room_id)` — только участникам; поля `parties`, `terms`, `accepted_at`, `receipt_id`; никаких `verified: true` без двух подписей;
- LLM-агент может **предложить** текст условий, но не может «подтвердить» их за человека; в ответах модели это явно ограничено schemas.

**Тесты:** один субъект не может «согласовать» в одиночку; чужая комната → `403`; повтор → тот же receipt; изменение условий после accept → новое предложение, старый receipt не перезаписывается.

**Замечание:** это расширение продукта. В основном проекте комнаты — «общие, не приватные переговоры» (`AGENTS.md`). Прежде чем добавлять терms-обмен, нужно решение владельца о том, что такое «соглашение» в этой модели и какие у него юридические последствия. Без этого I3 остаётся дизайн-наброском.

## 5. I4 — витрина: перенос UI-паттернов

Из React-прототипа переносится не код, а решения:

- чипы категорий/секций и «хлебные крошки» — уже есть в `public_web.py:28-115`, можно довести до вида прототипа;
- карточка: цена/«договорная», способ передачи (самовывоз/доставка/онлайн), состояние, «автор отвечает в комнате» — при условии, что все поля есть в allowlist `listing_contract`;
- пустое состояние и фильтр по секциям — есть (`/market/section/<id>`), добавить мобильную вёрстку;
- **не переносить**: кнопки «опубликовать»/«прикрепить фото» на витрине — веб-запись остаётся за гейтом M3b.3.

Этот пункт можно делать сейчас: он не меняет контракты и не создаёт write-path.

## 6. I5 — пример клиента с tool-calling

Прототип показывает рабочий цикл «модель → function call → выполнение → второй проход». В основном проекте такого примера нет, а он нужен: пользователь приходит со своим агентом.

**Форма:** `clients/gemini/` (по аналогии с `clients/qwen/`): README + скрипт, который подключается к **кандидату** по Streamable HTTP с Bearer-ключом, получает `tools/list`, отдаёт схемы модели, исполняет `tools/call`. Ключ Gemini — только из env, `.env.example` без значения. Сервер о модели не знает: провайдер-агностичность сохраняется.

**Гейт:** пример не входит в пакет, не запускается в CI против реального API; CI проверяет только импорт/линт и оффлайн-мок.

## 7. I6 — эргономика демо

- `docker compose`-профиль `demo` с флагом `DEMO_SEED=1` (в прод-профиле флаг отсутствует) — идея прототипа, но с явным разделением;
- один healthcheck-эндпоинт (`/healthz`) с проверкой БД, чтобы smoke был одинаковым в CI и на VPS;
- `.env.example` с пустыми значениями — у прототипа его нет, у основного проекта тоже стоит проверить.

**Не переносить:** «1 команда до продакшена». Демо-профиль не должен уметь включаться в production-конфигурации; тест: `DEMO_SEED` в `NODE_ENV=production`-эквиваленте → отказ старта.

## 8. Порядок работ (в терминах основного проекта)

| Шаг | Содержание | Когда |
| --- | --- | --- |
| A | I4 — витрина, read-only, без контрактов | можно сразу |
| B | I5 — пример клиента Gemini | можно сразу, отдельный PR |
| C | I6 — healthz + demo-профиль + `.env.example` | можно сразу |
| D | I1 — матчинг | после приёмки первого реального сценария **и** decision record |
| E | I2 — публичный SSE | после стабилизации публикации (Фаза 3 уже смержена) |
| F | I2 — приватные уведомления через SDK | после появления реальных тредов в TEST |
| G | I3 — terms/agreement | только после продуктового решения о природе соглашения |

Каждый шаг: contract → тесты (включая негативные) → `docs/ci-*.md` с evidence на SHA → обновление `project-status.json`/`work-state.json` → owner-approved PR. Никаких «заодно поправим».

## 9. Что категорически не переносить

1. Отсутствие модели доступа и дампы комнат.
2. Синтетические `executedTools` и любые «подтверждено», не подтверждённые записью в БД.
3. Хардкод фактов, цен и согласий в переговорах.
4. Авто-публикацию и `owner` из тела запроса.
5. Keyword-роутинг, выдаваемый за автономного агента.
6. Расширение категорий (`jobs`, `dating`, `rides`, `delivery`) до первого реального сценария.
7. `tsx` в production, root в контейнере, отсутствие lock-файла.
8. Унаследованную документацию прототипа (она и так из этого репозитория).

## 10. Итог

Прототип даёт основному проекту четыре вещи, которых в нём нет: асимметричный матчинг, паттерн real-time присутствия, UI-язык витрины и пример агентского tool-calling. Всё остальное — либо уже реализовано лучше (доступ, публикация, отзыв ключей, восстановление), либо не должно существовать (фабрикация вызовов и согласий).

Порядок A–C безопасен и полезен сейчас; D–G требуют изменения зафиксированного плана и отдельного решения владельца.
