# Координация сессий и распределение задач для AI-Агентов (Jules / Gemini)

Документ предназначен для координации совместной параллельной работы нескольких сессий AI-агентов (и людей-разработчиков) над проектом **MCP Rooms Marketplace (`LeonidYasin/mcp-rooms-googleai-2`)**.

---

## 📊 Оценка качества текущей координации (Evaluation)

### 🟢 Сильные стороны (Strengths)
1. **Единый источник правды:** Документ `docs/session_coordination.md` предоставляет общую картину распределения задач в проекте.
2. **Использование стандартизированного CLI:** Наличие `scripts/github_mcp_cli.py` позволяет агентам автоматизировать создание и слияние PR через MCP/GitHub API без использования сторонних UI.
3. **Строгое правило изолированных веток:** Именование веток по шаблону `feat/<task-name>` или `fix/<description>` снижает риск прямых конфликтов в веточке `main`.
4. **Обязательное тестирование:** Требование прохождения `npm test` (vitest) перед отправкой PR снижает риск регрессий.

### 🔴 Слабые стороны и узкие места (Bottlenecks)
1. **Отсутствие протокола захвата задач (Task Claiming Protocol):**
   - В текущем подходе нет четкого алгоритма, как сессия объявляет о начале работы над задачей со статусом `⏳ Ожидает`. Из-за этого две параллельные сессии могут одновременно взять одну и ту же задачу.
2. **Отсутствие тайм-аута неактивности (Stale Task TTL):**
   - Задачи в статусе `🔄 В разработке` не содержат отметки времени старта. Если сессия была прервана из-за сбоя или лимитов, задача остается "заблокированной" бессрочно.
3. **Отсутствие детализации затронутых файлов (Impact Area):**
   - В таблице указано только общее название задачи, без конкретных модулей и файлов (`server/auth.ts`, `server/db.ts` и т.д.). Параллельные сессии могут правящие пересекающиеся файлы, что приводит к сложным git-конфликтам.
4. **Отсутствие журнала передачи контекста (Handover & Blockers Log):**
   - При появлении нетривиальных блокеров или промежуточных архитектурных решений нет формализованного места для передачи контекста между сессиями.
5. **Отсутствие правил изменения схем БД и API:**
   - Нет протокола согласования несовместимых изменений (breaking changes) в схеме SQLite или спецификациях MCP JSON-RPC.

### 2. Протокол взятия задачи в работу (Task Claiming Protocol)

Перед началом выполнения новой задачи сессия **обязана**:
1. **Проверить пересечения по файлам (File Impact Analysis):**
   - Убедиться, что планируемые к изменению файлы не находятся в процессе редактирования другой активной сессией (`🔄 В разработке`).
2. **Захватить задачу (Claim Task):**
   - Открыть `docs/session_coordination.md`.
   - Изменить статус с `⏳ Бэклог` на `🔄 В разработке`.
   - Указать имя сессии, название создаваемой ветки, затронутые файлы и текущее время UTC.
   - Закоммитить и слить/отправить изменение в координационную документацию.
3. **Правило TTL неактивности (Stale Task Timeout = 2 часа):**
   - Если задача находится в статусе `🔄 В разработке` без обновлений более **2 часов**, она считается брошенной (Stale Task).
   - Другая сессия имеет право сбросить статус на `⏳ Бэклог` или перехватить задачу, оставив запись в журнале передачи контекста.

### 3. Пошаговые правила совместной работы

1. **Создание и именование веток:**
   - Шаблон имени ветки: `feat/<название-задачи>` или `fix/<описание-бага>`.
   - Никогда не коммитьте напрямую в `main` / `master`.

2. **Запуск тестов и линтера перед PR:**
   - В обязательном порядке запускайте полную проверку перед отправкой изменений:
     ```bash
     npm run lint
     npm test
     npm run build
     ```

3. **Создание и слияние PR с помощью CLI:**
   - Для создания PR используйте встроенный скрипт:
     ```bash
     GITHUB_TOKEN="$TOKEN" python3 scripts/github_mcp_cli.py --repo LeonidYasin/mcp-rooms-googleai-2 prs create \
       --title "feat: описание задачи" \
       --head <branch> \
       --base main \
       --body "Описание внесенных изменений и проверок"
     ```
   - Если CI проходит успешно, выполните автоматический merge:
     ```bash
     GITHUB_TOKEN="$TOKEN" python3 scripts/github_mcp_cli.py --repo LeonidYasin/mcp-rooms-googleai-2 prs merge --number <PR_NUM>
     ```

4. **Атомарность и миграции (DB & API Schema):**
   - Изменения в схеме SQLite (`server/db.ts`) должны сопровождаться обратной совместимостью или скриптами миграции.
   - При добавлении/изменении эндпоинтов MCP JSON-RPC обязательно обновляйте манифест `tools/list`.

5. **Обновление статуса в `docs/session_coordination.md`:**
   - После успешного слияния PR отмечайте статус `✅ Завершено` и указывайте номер merged PR.
